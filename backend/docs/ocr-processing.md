# Local text extraction and OCR

Implemented 5 November 2026. A clinician with access to the patient opens Documents, uploads an original, and selects **Start extraction**. The separate worker processes the queued document. On completion, **View extracted text** shows each page as an unreviewed draft. Originals remain downloadable for comparison.

## What the code does

- `app/processing.py`: authorises start/retry/cancel, returns completed draft pages and lists recent processing jobs for operations administrators.
- `app/worker.py`: claims durable PostgreSQL jobs, processes pages, encrypts results, records progress and audit events. Run it separately from FastAPI.
- `app/extract_page.py`: runs page processing in an isolated child process. PDFium reads existing text and renders scanned pages; local Tesseract recognises image text. Original bytes and rendered images travel through memory/pipes rather than plaintext temporary files.
- `ExtractionJob`: one current processing record per document. States are queued, running, completed, failed and cancelled.
- `ExtractedPage`: numbered encrypted text records, including extraction method and a no-readable-text flag.
- Migration `0006_extraction`: creates the queue and page tables.
- Documents screen: start, retry, cancel, progress refresh and result link. A separate extraction viewer displays draft text. The existing review/import editor is not connected yet.

## Start on this Mac

Tesseract was already installed and the OCR worker was started during implementation. To restart later, open another terminal:

```sh
cd /Users/testuser/Desktop/sanctum/backend
source .venv/bin/activate
python -m app.worker
```

Keep FastAPI, the frontend and this worker running. Stopping the worker does not lose queued jobs. The worker waits for jobs in PostgreSQL; it does not need Redis or a cloud service.

On another machine, install the updated Python requirements, install Tesseract and its English language data, and run `alembic upgrade head`. On macOS, Tesseract can be installed with `brew install tesseract`. On Debian/Ubuntu, use the system packages `tesseract-ocr` and `tesseract-ocr-eng`. Check with `tesseract --list-langs`.

`TESSERACT_COMMAND` defaults to `tesseract`, but can be an absolute executable path. `OCR_LANGUAGE` defaults to `eng`; additional languages require installed Tesseract data. The child-process timeout cleanup currently targets macOS/Linux; use Linux/WSL for Windows deployment.

## How processing works

1. The API checks document-writing permission, clinical-read permission, patient access and active patient status.
2. Start creates a queued job; the original file remains encrypted in storage.
3. A worker claims one job with a database row lock. Multiple PostgreSQL workers skip already-claimed jobs.
4. The worker decrypts the original, extracts one page at a time and persists each result encrypted.
5. A PDF page with at least 20 alphanumeric text characters uses its embedded text. Sparse/image-only pages and JPEG/PNG files use OCR. This heuristic may miss image text on a mixed-content page with a substantial text layer; compare the original.
6. Progress reflects completed pages. The API exposes page text only when the entire job is completed. It never silently marks the output reviewed.
7. A blank or unreadable page returns empty text and a warning rather than invented content.

Tesseract is suited to printed text. Handwriting, poor scans, tables, unusual fonts and medical notation may be misread. Current tests establish basic synthetic printed-text operation, not clinical transcription accuracy. No AI summary is generated by this feature.

## Reliability and access

- Each claim has a run ID and a 180-second lease renewed after every page. Interrupted jobs can be reclaimed after expiry. Three interrupted attempts require a manual retry.
- A page child process is limited to 90 seconds; its OCR subprocess to 60 seconds. Rendered images are limited to 20 megapixels and extracted page text to 100,000 characters. File/page limits from upload continue to apply. Production deployment still needs process/container memory and concurrency limits.
- Cancellation immediately changes the job state and deletes partial stored results. An in-flight page may run until it finishes or times out, but its output is discarded. Stale workers cannot overwrite a newer attempt.
- Retry is allowed for failed/cancelled jobs and restarts extraction. Completed documents cannot be re-extracted through this endpoint, preventing accidental replacement of text later used for review.
- The worker rechecks the requesting account, patient status and patient access when claiming and before publishing every page. Revocation or archival cancels the work and removes partial results.
- Read access is checked on every page request. Administrators with only operations permission can see job IDs, states and generic errors, but not clinical text.
- Fixed error messages are stored; raw parser errors and clinical text are not logged.
- If the worker is stopped, jobs remain queued. The UI currently does not provide a worker heartbeat indicator; check the worker terminal.

## API

Relative to `/api/v1/patients/{patientId}/documents/{documentId}`:

- `POST /process`: queue extraction; returns 202 with a job record.
- `POST /retry`: restart failed/cancelled extraction; returns 202.
- `POST /cancel`: cancel queued/running extraction.
- `GET /pages`: completed, encrypted-at-rest page results with filename, page numbers, raw text, method, unreadable flag and `reviewState="unreviewed"`.

`GET /api/v1/admin/operations/jobs` returns the latest 100 job records for `operations:manage` accounts. The document listing includes `jobState`, `progress`, `processingMessage` and the `extraction` allowed action when ready.
